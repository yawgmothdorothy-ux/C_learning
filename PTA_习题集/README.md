## 今天最值得保留的思路

### 从条件推导枚举范围

特殊方程题不应把循环范围随手设成 70 或 75。由 `X ≤ Y` 和 `X² + Y² = N` 得到 `2X² ≤ N`，外层按 X 递增枚举，内层从 Y=X 开始，既满足约束，也保证输出顺序。

支票题同样利用变量范围：分数只有 0～99。枚举 f 后，检查 `98*f - n` 是否非负、是否能被 199 整除，就能确定整数元数 y。范围很小时，直接枚举比通用整数方程算法更容易实现和验证。

### 先确定过程，再选择算法

蠕虫每分钟的动作是固定的，没有多种方案可供选择。只需维护高度和时间，不需要用 `max()` 拼出一个 DP 递推。上爬达到井口后立即结束，最后一次没有休息和下滑。

数字陷阱只依赖上一步的数字，不需要保存整个历史数组。保留当前值和下一步值即可；让结果保持不变的那一步也必须输出。例如输入 5：

```text
1:16
2:22
3:13
4:13
```

### 用反例检查边界

样例通过只说明样例正确。今天发现问题的反例包括：

- 三个数 `2 1 3`：中间值在数组首位，不能从下标 1 才开始查找。
- 三个数 `1 1 2`：中间值可以与最小值相同，排序比排除最大最小更可靠。
- 方程输入 `9800`：必须包含 `70 70`，循环的上限不能漏掉等号。
- 超速输入 `110 100` 和 `150 100`：分别检查 10% 和 50% 的处罚边界。
- 陷阱输入 `13`：第一步仍应输出 `1:13`，随后结束。

## C 语言调试笔记

| 问题 | 原因与修正 |
| --- | --- |
| `main` 找不到 | 曾写成 `mian`；入口函数必须叫 `main` |
| `fact()` 未声明 | `<math.h>` 不提供阶乘函数；必须定义自己的函数，且其他独立 .c 文件不会自动带入它 |
| 数学函数链接失败 | Linux 下编译时添加 `-lm`；只有 `#include <math.h>` 不够 |
| 循环不结束 | `i+2;`、`n/10;` 只计算，不更新变量；应写 `i += 2;`、`n /= 10;` |
| 求和结果不确定 | `sum` 未初始化；累加之前设为 0 |
| 区间判断永远成立 | `80 <= n < 90` 在 C 中不是数学区间；用 `n >= 80 && n < 90` |
| 字符统计随机 | `%c` 默认只读一个字符，不能据此遍历未赋值的整个数组 |
| 指针写入报错 | `int *N;` 不会分配数组；没有有效内存就不能使用 `*N` 或 `N[i]` |
| 输出整数或浮点数错误 | `printf` 接收变量值，不是 `&变量`；`%d`、`%ld`、`%lld`、`%f` 要与类型匹配 |
| 输入浮点坐标 | `double` 配合 `scanf("%lf", &x)`；检查返回值能判断是否读入成功 |
| 输出百分号 | `printf` 中用 `%%` 表示一个 `%` |
| 多个结果连在一起 | 每条结果末尾补 `\n`，特别是无效输入分支 |
| `scanf` 返回值警告 | 属于警告，不等于算法错误；用返回值检查实际读入的变量数 |

终端显示也遇到过异常：同一程序在外部终端输出完整，在某些 VS Code 窗口中缺少第一行。从独立配置目录启动的测试窗口能正常显示，但当时同时改变了配置、扩展和 GPU 设置，尚不能确定唯一原因。不能把终端显示异常直接归因于 C 代码。

## 编译与运行

每个源文件是一个独立程序，各自包含 `main()`。一次只编译一个练习，不要将整个目录的 .c 文件一起链接。

在本目录执行：

```bash
gcc -std=c11 -Wall -Wextra -g Loops_循环与数学/PTA26.c -o Loops_循环与数学/PTA26 -lm
./Loops_循环与数学/PTA26
```

目录内的 `.vscode` 提供“运行当前 C 文件”配置，构建任务已包含 `-lm`。打开本目录后，选择该配置，切回目标 .c 文件并保存，再按 F5。仓库根目录也保留了相应配置，适用于打开整个 `C_learning` 项目的情况。

`-lm` 一次链接标准数学库即可使用 `sqrt`、`pow`、`fabs`、`hypot` 等函数，不需要逐个安装。编译产生的同名可执行文件通过 `.gitignore` 排除，仅提交源码、说明和配置。
